## 修复方式

### 成员名称与脚注

源文件的 Table 9 已将四个脚注数字压平到 BrowseName 中。实体结构和原文表格因此同时出现这些 token，模型会直接照抄；仅要求“不编造”不能修复已经存在于输入中的转录歧义。

|---|---|---|
| ServerStatus1 | ServerStatus | §6.3.1，L234 |
| ServerCapabilities1 | ServerCapabilities | §6.3.1，L239 |
| ServerDiagnostics1 | ServerDiagnostics | §6.3.1，L240 |
| ServerRedundancy1 | ServerRedundancy | §6.3.1，L242 |

去掉数字的拼写也与本地 §6.3.1 成员说明及 §8.3.2 Table 112 的 Server 成员路径一致；后者分别见 L2733、L2770、L2823、L2737。本轮没有核查官方 PDF 或宣布官方勘误。

在共享证据构建路径中，仅对 §6.3.1 内上述四个确切的 HasComponent 行增加 **Transcription note**。说明明确标为“派生转录说明，非原文措辞”，列出原始 token 到成员名的对应关系。原始正文逐字保留，回答可以解释两种拼写的关系并引用原始记录。

说明与证据一起计算字符预算，模型上下文、序列化 snippet 和离线回退保持一致。没有事后替换模型回答，也没有通用删除名称末尾数字的规则；合法的 Channel1 等名称保持原样。原始生成数据仍保留转录拼写，本轮解决的是问答证据阅读歧义，未重建实体或图谱。

### 证据不足时的回答

收紧共享系统要求，使两种检索组都遵守：

- 按用户实际请求逐项回答，仅列出已有证据支持的事实；即使放在“缺失内容”标题下，也不能凭记忆补参数、状态、转换或示例。
- 审计／诊断记录提及服务名不等于给出了协议定义。用户请求完整 Service 请求／响应或 Session 状态机而证据不足时，应说明需要 OPC 10000-4，并明确请求对应材料。
- 区分 Services 与地址空间 Methods；Part 5 可以定义 Method，不能将其定义一概归到 Part 4。
- 版本比较需要两个已标识版本的来源或权威变更日志。兼容性注释不能证明相对上一版的变化；缺材料时请求上一版文档或官方日志，不猜上一版本号。
- 材料请求仅针对实际问题缺失的证据，不应扩展为假设后续问题的材料清单。

这些是生成约束，不是通用语义验证器。原有引用白名单、登记表、严格标签校验、原文优先预算及 Wiki 草稿标识继续保留；没有增加模型重试或自动补充外部规范。

## 局限与剩余问题

本轮没有扩大术语表、改候选排序或重编 Wiki，脚注处理仅针对四个核实的本地转录问题。未来若出现其他脚注格式，应以源格式或明确交叉证据处理，不能直接扩大为删数字规则。

同一题集已被用于定位问题，不是独立未知测试集；没有盲评、人工签署、统计显著性分析或重复随机采样。候选轮被用于修改提示，最终整轮重跑是开发复测，不应伪装成独立评估。温度 0 也不保证输出完全可重复。

当前仍有以下限制：

- **Q09 混合组：** 原文是 null string，回答写成“空字符串”。fallback 与 Severity 正确，但 null／empty 不能互换，因此只计 1.5/2。未通过挑选第一候选答案掩盖该退化。
- **Q15 混合组：** 先说 Part 5“仅在审计语义”提及 CreateSession，下一条又列出诊断 sessionName，前句范围过窄；其拒绝编造和材料请求仍满足本题严格要求。
- **Q01、Q09 混合组：** 英文问题得到中文回答，语言跟随要求未完全执行；不改变事实评分。
- **Wiki 引用：** 个别回答把 Wiki 标签与原文标签并列，但关键事实均有原文支撑。未作所有句子的引用精确率审核，不能宣称每条附加说明都已验证。
- **生成边界：** 本次 Q15/Q16 通过不能证明所有范围外问题都会安全拒答。系统要求属于软约束，现有严格校验只保证引用格式和标签成员关系，不验证所有语义蕴含。

可确认的收益是：本组脚注名称错误已消除，两个边界题均明确请求缺失材料，引用链与原文定位保留。混合组整体正向分数持平且仍有一处误译，不据此宣称混合检索优于纯原文 RAG。
